# Passage ranges

Prerequisites: a paired file book with its BGE-M3 index complete, and the existing Cloudflare account configuration. Legacy page-aligned imports are unchanged. No additional model, dependency or account setup is required.

## Use and validation

- In automatic search mode, opening/clicking a substantive translated paragraph starts bounded refinement if no current cache exists. Its source area remains readable while positioning runs; the search controls stay available. First-time refinement sends the paragraph, up to four neighbors and candidate sentence/clause windows to Cloudflare BGE-M3. Cached results are local. Text-only mode does not initiate cloud refinement; cached ranges still display. More → retry refinement is an explicit cloud action.
- The same local source corridor is split at sentence/clause boundaries. Joined PDF continuations are modeled together; a local optimizer selects non-overlapping ranges in translated-paragraph order. Weak similarity, implausible length coverage, invalid offsets, missing data or network/quota failure leave no unreviewed passage highlight. Thresholds are heuristics, not calibrated correctness probabilities.
- Check both ends of a passage, adjacent paragraphs and page crossings. Only selected source character ranges are highlighted; other source context remains unhighlighted. Inference is labeled as a candidate. A human confirmation saves the complete range, not merely its first original unit. Cancelling a confirmation leaves the model candidate available.
- Model-view normalization recognizes PDF running headers, normalizes Unicode, joins common line hyphenation and tracks every retained character back to the unchanged raw unit. Display/copy keeps original extraction artifacts. Browser offsets use Unicode code points to match Python offsets.

## Bounds, storage and recovery

- Source context is capped at 18000 characters and constrained to within four original units of the retrieved anchor. Candidate windows contain up to 12 clauses and 2400 characters. A refinement request allows at most 1200 distinct fragments and 800000 input characters, with 24 texts per batch and one refinement at a time. This limits work; it is not a provider billing cap. Excessive candidates abort rather than silently omitting arbitrary fragments.
- SQLite `alignment_vectors` stores book-scoped hashed fragment vectors. `passage_cache` stores inferred raw ranges or uncertainty, versioned against the algorithm/model and paired file hashes. `passage_reviews` stores human-confirmed ranges alongside the existing `file_reviews` anchor. Cache hits do not call the provider; completed vector batches survive a failed request. Failed requests cool down for five minutes unless explicitly retried. A changed algorithm/model/file invalidates its model range cache; human reviews are preserved.
- These tables live in the existing ignored library database. Retain them while the book is retained, with no automatic cleanup producer. They are included in the same full-database-plus-files recovery procedure. No book text, vectors, private paths or runtime database belongs in public Git. Development diagnostics remain in ignored local/QA directories under the existing 14-day diagnostic policy.
- The schema change is additive. Before rollback, preserve the complete database and retained files together. Older app versions ignore fine ranges and can display a confirmed anchor as a whole-unit mapping; do not use them to assess new passage confirmations. Prefer fixing forward after range reviews have been saved. No existing files, coarse vectors, page mappings or confirmations are deleted by this migration.

Known limits: local order assumptions do not cover every reordered translation, omission or footnote. OCR punctuation may corrupt splitting. Long paragraphs and sparse/short labels can remain uncertain. No whole-book accuracy guarantee or word-level mapping is implied by a range candidate.
